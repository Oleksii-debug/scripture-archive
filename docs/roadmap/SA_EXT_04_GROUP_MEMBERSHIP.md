# SA-EXT-04 — group membership lifecycle

The group page provides member/facilitator exit, ownership transfer to an existing member or facilitator, and confirmed owner deletion. An owner must transfer responsibility before leaving, or explicitly delete the group. Transfer changes the authoritative group owner and both membership roles in one D1 transaction. A failed or stale transfer cannot partially change roles. The owner-only transfer roster includes private member names and identifiers; ordinary members and visitors do not receive that roster.

Leaving removes membership, invalidates active group attempts, and consumes outstanding group reading receipts in one transaction. It does not delete historical meeting records or completed personal results. A grading result remains recoverable as a personal result using the existing finalization guard. No profile is required to leave. New requests after leaving cannot access private group data. A facilitator's meeting insertion checks membership again inside the write transaction, so a prior permission lookup cannot authorize a write after membership has changed.

Deleting requires both authoritative ownership and an owner membership, plus an explicit confirmation field. The transaction invalidates active group attempts and consumes group receipts before deleting the group. Existing foreign keys cascade memberships, sessions, group answers and marathon registration. Other groups and completed personal attempt history remain. Native select/button controls have labels, confirmation dialogs and status text in the three existing interface languages.

Verification includes the actual TypeScript handlers against SQLite loaded from all repository migrations, injected transaction failures, concurrent transfers, stale facilitator authorization, private roster checks and markup escaping. The local Worker HTTP integration exercises the full create/join/transfer/leave/delete sequence using two independent authenticated accounts. This is not physical NVDA or browser acceptance, and does not claim production deployment.

Known limits: leaving is an opt-out, not a ban; a former member who knows a still-valid invite can rejoin. Invitation rotation, member role management and broader marathon scheduling remain separate work. Concurrent requests already in progress before a membership change may have read authorized data before that change; this feature cannot retract responses already received.
